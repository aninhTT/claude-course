# Lesson 6.04: Polish & Share

## Learn

You've built two real use cases. That's a genuine accomplishment — you went from "I wonder if AI could help with..." to "here's a working thing that actually does it." Take a moment to appreciate that.

Now let's take your best build from "works for me" to "shareable with others."

### The Polish Checklist

Going from personal tool to shared resource requires attention to a few things:

**Documentation**
- Does it have a README or description that explains what it does?
- Are the instructions clear enough for someone who didn't build it?
- Are there examples of expected input and output?

**Packaging**
- Are files organized logically? (Not scattered across random folders)
- Are file names descriptive? (`weekly-digest-skill.md` not `test3-final-v2.md`)
- Is there anything that should be cleaned up or removed? (Debugging notes, test files, half-finished experiments)

**Clarity**
- If it's a skill, are the instructions unambiguous?
- If it's a workflow, are the steps in the right order?
- Could someone run this without asking you questions?

### Sharing Options

There are several ways to share what you've built:

- **Skill file** — Share the SKILL.md file directly. Someone copies it into their `.claude/commands/` folder and they have it.
- **GitHub repo** — Push it to a repository (you'll learn more about this in Module 7). Great for versioning and collaboration.
- **Slack or team channel** — Post the skill file or a description of what you built. Quick and informal.
- **Zip folder** — Bundle everything into a folder someone can download. Low-tech but effective.
- **Demo** — Show someone in a 1:1 or team meeting. Sometimes the best way to share is to demonstrate.

### Getting Feedback

Real feedback from real users is invaluable. When sharing, ask:
- "Does this solve a problem you actually have?"
- "Is anything confusing about how it works?"
- "What would make this more useful for you?"

Don't ask "is it good?" — that invites a polite yes. Ask specific questions that invite honest, actionable feedback.

### Celebrate What You've Built

Seriously. Most people talk about AI use cases in the abstract. You've built real ones that work with your actual tools and data. That's the difference between understanding AI and using AI.

## Practice

Pick your best build and polish it for sharing.

**Step 1:** Choose which build to polish — your best, most useful, or most interesting one.

**Step 2:** Add documentation:
- Create a README or description section at the top of the file
- Explain what it does, who it's for, and how to use it
- Include an example of what the output looks like

**Step 3:** Clean up:
- Rename files to be clear and descriptive
- Remove any debugging artifacts or test files
- Organize everything into a logical structure

**Step 4:** Test the "cold start" — pretend you've never seen this before. Read the instructions from scratch. Could you run it successfully based solely on what's written? If not, improve the docs.

**Step 5:** Prepare to share. Pick a sharing method (skill file, Slack post, demo, etc.) and get it ready.

**Success criteria:** Polished one build with clear documentation, clean file organization, and descriptive naming. Prepared it for sharing via at least one method.

## Challenge

Actually share one of your builds with a colleague or team. Get real feedback.

**Step 1:** Choose your audience. This could be:
- A teammate who has similar workflows
- Your manager (show them what you've been learning)
- A Slack channel where people discuss tools and productivity
- A colleague in a 1:1

**Step 2:** Share it. Pick the method that fits your audience:
- Post the skill file in a team channel with a brief description
- Demo it live in a meeting
- Send someone the file with instructions
- Push it to a shared GitHub repo

**Step 3:** Collect feedback. Ask at least one specific question:
- "Would you use this? Why or why not?"
- "What would you change?"
- "Does anything confuse you about how it works?"

**Step 4:** Document the feedback in `workspace/sharing-feedback.md`. What did you learn? What would you change based on the feedback?

**Success criteria:** Shared a build with at least one other person. Collected and documented specific feedback. Identified at least one improvement based on the feedback.
